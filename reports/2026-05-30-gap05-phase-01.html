01 / Input -> Output

Input -> Output Summary

Inputs

  • An 8760-hour factory load profile (loads_kw) — validated against the real saigon18 profile (peak 30,246 kW, 184,262 MWh/yr).
  • Two regime ids from vn_regime_registry_2026.json (e.g. decision_963_2026_current, decision_14_2025_legacy).
  • Customer type + voltage level (e.g. industrial, medium_voltage_22kv_to_110kv).
  • Existing tariff engine: build_vietnam_tariff(), resolve_vietnam_regime(), convert_usd_to_vnd().

Outputs

  • regime_impact.py with compute_regime_impact(...) -> RegimeImpact.
  • RegimeImpact / RegimeSide / RegimeDelta dataclasses with a to_dict() for downstream artifacts.
  • Per-regime annual bill (VND) + peak / normal / off-peak consumption (MWh).
  • A→B delta: bill delta (VND), delta %, peak-hours-changed, peak-consumption delta.
  • 7 passing unit tests; 107 existing reopt tests still green.

03 / Math / Algorithm Used

Math / Algorithm Used

QuantityFormulaNotes
Annual energy bill Σ<sub>h=0..8759</sub> load[h] · rate[h] rate[h] from build_vietnam_tariff() (USD/kWh), per regime.
Demand component Σ<sub>m=1..12</sub> max(load in month m) · demand_rate[m] Zero for most regimes; non-zero under the Decree-146 two-part trial.
VND bill (energy_usd + demand_usd) · exchange_rate Round-trips the engine's VND→USD conversion via convert_usd_to_vnd().
Consumption buckets Σ load[h] over hours of class ∈ {peak, standard, offpeak} Class from regime TOU windows; same Mon-Sat / Sun calendar as the rate builder.
peak_hours_changed |peak<sub>A</sub> △ peak<sub>B</sub>| (symmetric difference) 963 {17–22} vs 14 {9,10,17,18,19} → {9,10,20,21,22} = 5.
delta_pct (bill<sub>B</sub> − bill<sub>A</sub>) / bill<sub>A</sub> · 100 Delta convention is B minus A ("from A to B").

The full pass is a single O(8760) loop per regime — two regimes, no optimization, no network calls. That is what keeps the toggle inside the < 1 s demo budget.

04 / Tools / Formulas / Methods

Tools / Formulas / Methods

  • Reused engine: build_vietnam_tariff() for the 8760 TOU rate series; resolve_vietnam_regime() for regime-specific TOU windows; convert_usd_to_vnd() for currency.
  • Calendar parity: hour classification mirrors preprocess._build_8760_rates exactly (weekday schedule Mon-Sat, Sunday schedule on Sundays) so classes line up 1:1 with the rate array.
  • Data-driven, not hardcoded: all windows and multipliers come from vn_regime_registry_2026.json / vn_tariff_2025.json, satisfying constraint CON-001 (support both 963-multiplier cases as scenarios).
  • Testing: pytest, TDD red→green; tests/python/reopt/test_regime_impact.py (7 tests).
  • Fixtures: real saigon18 8760 load, a synthetic flat load, and a morning-peaky load to assert load-shape sensitivity.

06 / Limitations / Second-Best Alternative

Limitations / Second-Best Alternative

  • Tariff-math only, no optimization. PHASE-01 prices the load as-is under each regime; it does not re-dispatch behind-the-meter assets. Solar/BESS value estimation arrives in PHASE-02.
  • 365-day calendar. The 8760 model uses a non-leap year and a Mon-Sat / Sunday split, matching the existing rate builder — public holidays are not individually modeled.
  • Demand charge is simplified. Monthly peak × flat demand rate; only the Decree-146 trial regime carries a non-zero rate today.
  • Second-best alternative: run a full Julia REopt solve per regime for true optimized bills. Rejected (ALT-001) because a 30–60 s solve per regime destroys the "instant toggle" demo experience — the whole point of GAP-05.

Errors / Warnings / Flags Encountered

  • Resolved — RISK-01-01: feared build_vietnam_tariff() might not support regime-specific windows. It already accepts a regime_id, so no extension was needed.

  • No regressions: 107 existing reopt unit + data-validation tests pass (one pre-existing expected UserWarning about export fractions).
