01 / Executive Summary

Executive Summary

What was wrong

Decree 243/2026/ND-CP, effective 2026-06-26, raised Vietnam's rooftop-solar surplus export cap from 20% to 50%. A research brief documenting this landed in the repo on 2026-06-30, but the data layer, both preprocessing language twins (Python and Julia), and the settlement engine still enforced the repealed 20% cap on every run. Every onsite analysis produced since June 26 understated exportable surplus energy and revenue.

What was done

A new versioned data file makes the 50% cap the active default while a named legacy regime preserves exact reproducibility of pre-Decree-243 results. Both language twins were fixed so their "non-default value" warning tracks the live regulatory default instead of a hardcoded 20%. A tested delta module quantifies the first-order revenue effect on the tracked Saigon18 golden run. Three independent webapp hardening gaps (path traversal, restart-stranded runs, invisible provenance) were closed alongside, plus the previously-untracked planning documents for this and the adjacent CI-truth sprint were committed so they no longer live on a single machine.

02 / Background & Objective

Background & Objective

reopt-pysam-vn models solar/wind/storage/DPPA economics for Vietnam using NREL REopt.jl plus PySAM, with a Vietnam-specific policy data layer (data/vietnam/) that both a Julia module and a Python module read identically. That data layer is the mechanism by which the repo is supposed to stay current with Vietnamese energy regulation — a change in law should be a new versioned JSON file plus a one-line manifest flip, not a code change. A same-day brainstorm (research/2026-07-18-execution-debt-decree-243-brainstorm.md) found that this mechanism had gone unused for three weeks despite the relevant research already being in the repo: the export-cap data file still said 20% when the enacted law said 50%. The objective of this effort was to close that gap correctly (new versioned file, not an in-place edit, with the old regime preserved for reproducibility), quantify its practical effect on a tracked example run, and use the same session to close three small, previously uncatalogued webapp hardening gaps found during the same review pass.

05 / Methodology

Methodology

Every phase followed test-first development: failing tests were written and confirmed red before any implementation code changed, matching the repo's own lessons.md convention of calibrating tolerances against reality rather than guessing. Data-layer changes used the repo's existing versioning discipline — a new file plus a manifest pointer, never an in-place edit of a file other results depend on for reproducibility. Every phase that touched the shared Vietnam preprocessing logic was verified against both language implementations (Python and Julia) plus the repo's own Julia↔Python cross-validation harness, since the two engines are required to produce byte-identical output. The Samsung/TTC bit-exact golden-parity gate was re-run after the data-layer change specifically to confirm — not assume — that the offsite CfD finance path is independent of the rooftop export cap. A full-suite regression pass closed out the work, isolating two pre-existing, unrelated slow/live-network test files (confirmed via git diff to have zero relationship to any commit in this effort) so the remaining 578 tests could run to completion and be compared against the repo's documented five-test known-failure baseline.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Done  Phase 1 — Preserve Planning Artifacts

Four planning documents (this plan, its brainstorm, the adjacent CI-truth sprint plan and brainstorm) existed only as uncommitted files on one machine — a single git clean away from being lost. They were committed, the KBC pro-forma cross-check script was relocated from a forbidden flat script path to its canonical scripts/python/pysam/ location, and a new docs/regulatory-watch.md table was created mapping every data/vietnam/ file to its governing regulation — born with the export-rules row marked STALE as the visible target for Phase 2.

Done  Phase 2 — Decree 243 Ingestion

A new vn_export_rules_2026_decree243.json became the active export-rules file (manifest flip); a new decree_57_2025_legacy regime reproduces pre-June-26 results exactly. Both preprocessing twins were fixed so the "non-default fraction" warning compares against the live regime-resolved value, not a hardcoded 20%. Full TDD coverage across Python and Julia test suites; Julia unit tests passed directly (60s); Julia↔Python cross-validation passed exact-match across all four exercised regimes; Samsung/TTC golden parity confirmed unaffected.

Done  Phase 3 — Export-Cap Delta Memo

A new library module plus CLI compares the old and new export-cap presets on the tracked Saigon18 golden run's fixed dispatch (explicitly not re-optimized) and writes a tracked markdown memo. Toy closed-form test case matched exactly. The memo's headline and its fixed-dispatch caveat are reproduced in the Findings section below.

Done  Phase 4 — Webapp Hardening

Three independent gaps found during the same review pass: a URL-supplied run_id was joined directly onto the storage root (path-traversal risk), a process restart left runs stuck forever in queued/solving, and a solve's provenance (solver, cache hit, policy data versions, wall time) was recorded but never shown. All three closed with tests; a live smoke test confirmed the traversal guard returns HTTP 404.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the export-cap gap is now closed, and it was a real, live currency defect. The repo now enforces the enacted 50% cap by default and warns only on genuine caller overrides. Pre-2026-06-26 results remain exactly reproducible via the new decree_57_2025_legacy regime, so no historical analysis is invalidated by this change — it simply stops projecting the old rule onto new work.

Finding 2 — the practical revenue effect, on a fixed dispatch, is real but should be read as a floor. On the tracked Saigon18 scenario-A golden run, moving from the 20% cap to the enacted 50% cap increases annual surplus export revenue by approximately 1,291,279,843 VND/yr (≈48,912 USD/yr at 26,400 VND/USD), with exported energy rising by roughly 1.92 million kWh/yr and curtailed energy falling by the same amount. This number deliberately does not re-optimize PV/BESS sizing under the new cap — a re-solved system would likely be sized larger and could capture more value still. The memo (reports/2026-07-18-decree243-export-cap-delta.md) states this caveat explicitly and flags re-optimization as follow-on work rather than folding an unverified number into the headline.

Finding 3 — the webapp hardening items were small, independent, and low-risk to fix now. None were exploitable beyond the local-only, single-user, no-auth threat model the webapp already documents for itself, but all three were cheap correctness/robustness gaps worth closing while already in the code: an unvalidated run_id could reach the filesystem layer with traversal characters, restart-stranded runs had no path back to a visible error state, and captured provenance data had no UI surface.

Recommendation. Ship these four phases as-is. The two follow-on items explicitly deferred by this effort — publishing the Decree 243 surplus pricing formula once EVN/NSMO releases a prior-year average, and a re-optimized (not fixed-dispatch) delta re-run — are correctly scoped as separate, smaller pieces of work rather than blockers on this remediation.
