01 / Executive Summary

Executive Summary

What was built

A new module, regime_impact.py, plus three CLIs, that price a factory's 8760-hour load under any two (or more) Vietnam regulatory regimes using the existing tariff engine — entirely in Python. It reports the annual EVN bill, the peak-window shift, and the avoided-cost value of solar and the arbitrage value of a battery under each regime.

Why it matters

Decision 963 (active since April 2026) replaced Decision 14's split TOU peak with a single evening peak. That reshuffle changes bills and undermines the morning-peak premium that solar and batteries used to capture. GAP-05 makes that financial impact visible instantly — the "wow factor" for the client demo.

Headline results (saigon18)

  • Bill: Decision 963 runs +2.57% vs Decision 14 for this load shape.
  • Solar avoided cost: −14.2% under Decision 963 (morning premium lost).
  • Battery arbitrage: ≈ 50% under 963 (one evening cycle vs two).
  • Decree-146 two-part trial: +19% from a new monthly demand charge.

Status & confidence

Complete and verified. Built test-first (red→green) each phase; full reopt suite passes (137 passed, 1 skipped) with zero regressions. Numbers are deterministic tariff math. Solar/BESS figures are clearly labelled demo-grade estimates, not optimized solves.

02 / Background & Objective

Background & Objective

The repository already had a capable Vietnam tariff engine: build_vietnam_tariff() builds an 8760-hour time-of-use (TOU) rate series for any regime in pure Python, and a regime registry (vn_regime_registry_2026.json) defines named bundles for Decision 14, Decision 963, and several forward-looking drafts. What it lacked was a way to compare regimes quickly: the existing path materialized full REopt scenarios and required a Julia solve (30–60 s each) for financial results — far too slow for an interactive demo.

Objective: a function — compute_regime_impact(loads, regime_a, regime_b, customer_type, voltage_level) — that returns the annual bill delta, the peak-hour shift, and a TOU consumption breakdown in under a second, Python-only. Then layer on the value impact for solar and storage, a machine-readable artifact, a CLI, and a shareable HTML report.

03 / Inputs & Scope

Inputs & Scope

Inputs & reused assets

  • Tariff engine: build_vietnam_tariff(), resolve_vietnam_regime(), convert_usd_to_vnd().
  • Regime registry & tariff data files (Decision 14, 963, forward drafts).
  • GAP-01 ingest_factory_load() for reading CSV/XLSX/JSON loads.
  • Real saigon18 load (peak 30,246 kW, 184,262 MWh/yr) for validation.
  • Research inputs on the TOU shift (2026-04-25, 2026-05-07 briefs).

In scope / out of scope

In scope: Python-only bill comparison; solar avoided-cost & BESS arbitrage estimates; multi-regime sweeps; forward-regime presets; a self-contained HTML report.

Out of scope (explicit): Julia solve integration, full REopt optimization under each regime, a web UI, and real-time streaming. These were deliberately excluded to protect the instant-toggle experience.

04 / Assumptions & Constraints

Assumptions & Constraints

Assumptions

  • ASM-001: bill impact = the 8760 TOU rate series applied to the load — no optimization.
  • ASM-002: solar/BESS value is estimated from load-shape analysis, not a full solve.
  • 365-day calendar, weekday (Mon–Sat) vs Sunday split — matching the existing rate builder; public holidays not individually modeled.

Constraints

  • CON-001: Decision 963 multipliers may not be final — MOIT has not confirmed whether Decision 14 multipliers are remapped or revised. Handled by keeping everything data-driven and supporting both as selectable scenarios.
  • DEC-001: the module lives at reopt/regime_impact.py, beside the regime runner.
  • BESS arbitrage is a theoretical maximum (perfect foresight, no efficiency losses) — explicitly labelled.
05 / Methodology

Methodology

Each phase followed strict red→green TDD: write the failing tests first, confirm they fail, then implement just enough to pass, then run the full reopt suite to confirm no regressions. Wherever possible the work reused existing engine functions rather than duplicating policy logic — the bill is computed in USD via build_vietnam_tariff() and converted back to VND, and the hour-by-hour TOU classification mirrors the engine's exact Mon–Sat/Sunday calendar so rate and class arrays line up 1:1.

Verification used a real factory load (saigon18), synthetic edge cases (a flat load and a morning-peaky load to prove load-shape sensitivity), and manual CLI runs that wrote and re-parsed JSON artifacts. After every phase the result was captured in an HTML phase report and committed/pushed to main.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 01 — Rapid bill comparison

Built compute_regime_impact() and the RegimeImpact/RegimeSide/RegimeDelta dataclasses. Computes per-regime annual bill (VND) and peak/standard/off-peak consumption, then the A→B delta and a peak_hours_changed count (symmetric difference of weekday peak windows = 5 for 963 vs 14). 7 tests; < 1 s confirmed.

Phase 02 — Solar/BESS value + CLI

Added estimate_solar_value_impact() (avoided cost = min(pv, load) × rate), estimate_bess_arbitrage_impact() (cycles/day = number of distinct daily peak windows), a combined RegimeComparisonArtifact, and the compare_regimes.py CLI. 6 tests. The battery insight: 963's single evening peak permits one cycle vs Decision 14's two, roughly halving arbitrage.

Phase 03 — HTML report + forward regimes

Added compute_multi_regime_impact() (sweep 3+ regimes vs a baseline), exposed FORWARD_REGIME_PRESETS, and built generate_regime_comparison_report.py — a self-contained Chart.js report with load profile, color-coded TOU windows, multi-regime bill bars, solar/BESS charts, and a regulatory timeline. 5 tests.

How the phases connect

Each phase strictly built on the last: the Phase-01 engine is the hot path Phase-02 prices assets against, and Phase-03 orchestrates both across multiple regimes and renders them. No phase reached forward; dependencies ran one direction only.

flowchart LR P1[Phase 01\nbill comparison engine] --> P2[Phase 02\nsolar + BESS value, CLI] P2 --> P3[Phase 03\nmulti-regime sweep + HTML report] P1 -. reuses .-> E[build_vietnam_tariff / resolve_vietnam_regime] P2 -. reuses .-> G[GAP-01 ingest_factory_load] P3 --> OUT[demo-ready report]
07 / Findings & Recommendation

Findings & Recommendation

The regime toggle is fast, accurate against the engine, and tells a clear story: Decision 963's evening-only peak window increases the bill modestly for a load like saigon18 (more consumption now lands in peak hours), while it erodes renewable value — solar loses its morning-peak premium (−14.2%) and a battery loses one of its two daily arbitrage cycles (≈ −50%). The Decree-146 two-part-tariff trial is the most dramatic mover, adding ~19% through a monthly demand charge.

Recommendation: adopt GAP-05 as the demo's regime-comparison surface. The rejected alternative — running a full Julia REopt solve per regime — was set aside because its 30–60 s latency destroys the instant-toggle experience that is the whole point. Keep the Python tariff-math path; reserve the solve for final, committed scenarios.

08 / Implementation Path

Implementation Path

Already shipped

All three phases are on main (commits 0f50400, 56167ca, 38ea63d). The module, three CLIs, 18 tests, and four HTML artifacts are in place.

To use it

Run python scripts/python/reopt/generate_regime_comparison_report.py --factory <load> --regimes 963,14,decree146 --solar-profile-synthetic --bess-power 1000 --output report.html, then open the HTML in any browser.

When MOIT publishes multipliers

Update the decision_963_2026_repriced_multipliers bundle in the registry — no code change needed (data-driven by design). The placeholder presets will then produce real deltas.

Optional extensions

Custom user-defined regimes ("what-if" peak-window sliders) and wiring the report into the broader demo flow alongside GAP-01..04 outputs.

09 / Risks / Open Questions

Risks / Open Questions

Risks & caveats

  • Two forward presets (decree57_rooftop_50pct_draft, decision_963_2026_repriced_multipliers) currently yield a zero bill delta — accurate to the registry today, but provisional until MOIT acts.
  • BESS arbitrage is a theoretical ceiling (no efficiency, no degradation, no demand-charge co-management).
  • Solar value is avoided-cost only — no export revenue or PV+BESS co-optimization.

Open questions

  • CON-001 (external): will Decision 963 remap or revise Decision 14's multipliers?
  • Q-001: support custom user-defined regimes, or pre-defined only? (Plan default: pre-defined.)
  • Confirm the B−A ("from A to B") delta convention is what the demo UI wants.
  • Make the BESS per-cycle energy duration configurable per C-rate.
