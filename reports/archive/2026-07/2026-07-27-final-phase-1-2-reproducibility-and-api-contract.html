01 / Executive Summary

Executive Summary

What was done

The first two of six phases in plans/2026-07-26-post-backlog-architecture-plan.md are complete and merged to main (commits 3943c5b, 31732d2). Phase 1 fixed a hidden Python 3.10 syntax error and brought the entire codebase to zero lint violations under a newly configured ruff gate, added that gate plus a Python 3.10 CI job, and pinned the PySAM dependency version in the package manifest instead of only in CI. Phase 2 gave the toolkit's public DealConfig input type a real structural validator backed by the JSON Schema the repo already ships but never enforced.

Why it matters now

This toolkit's output goes to external counterparties as decks and reports. A syntax error invisible to a single-version CI matrix, and a public input type that silently accepted anything, are exactly the kind of foundation-level gaps that should close before more deliverables get built on top — which is the explicit reason the underlying plan sequenced this work first, ahead of the larger config-driven case-runner initiative.

02 / Background & Objective

Background & Objective

A prior research pass (research/2026-07-26-reopt-pysam-post-backlog-architecture-brainstorm.md) found the toolkit's prior implementation backlog fully drained — every phase from the two most recent sprint plans had shipped and CI was green — and used that moment to look for structural gaps no test currently catches. It surfaced four: a Python-version mismatch between what the package declares and what actually parses; a public API that accepts arbitrary dicts while its headline correctness guarantee sits disabled; four different hardcoded currency conversion rates scattered across the codebase; and a Julia implementation twin that has quietly become a stale subset of its Python counterpart.

The six-phase plan that followed addresses all four, in a deliberate order: reproducibility and lint hygiene first (so every later change is verified on a clean, dual-version baseline), then the API contract, then the correctness-guarantee reconciliation, then the currency/assumptions unification, then the Julia archive decision. This report covers the first two phases, executed and verified end to end.

04 / Assumptions & Constraints

Assumptions & Constraints

Assumptions applied

  • The declared minimum Python version (3.10) is the real contract, not the 3.12-only interpreter CI happened to run — so the syntax error was treated as a bug in the affected script, not grounds to raise the floor.
  • No Python 3.10 interpreter was available on the execution machine (only 3.11, 3.12, 3.14 present); ruff's --target-version py310 syntax check served as the authoritative gate instead, and was confirmed clean.
  • jsonschema must not become a runtime dependency — the shipped schema file's own description promises none, so Phase 2 used a small hand-rolled validator covering only the three keywords the schema actually uses (required, type, enum).

Constraints honored

  • Never commit red: every change was verified against the full portable test suite before being staged.
  • ruff --fix's output was reviewed in full before applying — not blindly accepted — to rule out removal of any side-effecting or registry-pattern import.
  • 27 unused-variable warnings were resolved by prefixing the variable name with an underscore rather than deleting the assignment, since several right-hand sides are function calls with side effects; deleting them outright could have silently dropped real work.
  • The webapp's public form-to-DealConfig path was explicitly re-verified against the new validator before considering Phase 2 complete.
05 / Methodology

Methodology

Each phase followed the same discipline: implement the change, run the full portable test suite (the same filter CI uses: not network and not requires_artifacts and not golden_machine and not requires_julia), fix anything red before proceeding, then commit. Phase 2 additionally followed a red–green sequence — its 17 new tests were written and confirmed to fail with ModuleNotFoundError before the validator module existed, then confirmed to pass once it was implemented.

Before touching the CI matrix, the plan's own risk (a Python 3.10 job could fail simply because a dependency lacks a 3.10 wheel) was checked directly rather than assumed: pip download was used to confirm nrel-pysam==7.1.0 publishes both a Windows and a Linux manylinux2014 wheel for CPython 3.10, so the matrix could be added at full strength with no degraded fallback needed.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 1 — Reproducibility floor & lint gate

The starting point was a real bug hiding in plain sight: generate_cross_project_dashboard.py had a Python comment sitting inside an f-string's replacement field — syntax that only became legal in Python 3.12. Because CI ran exclusively on 3.12, the file silently compiled there while being a hard SyntaxError on the declared minimum version, 3.10. The fix moved the note out into an HTML comment in the surrounding template text, fully outside any Python expression — the first attempt (moving the comment just inside the enclosing braces) was still wrong for the same underlying reason, and was corrected before proceeding.

With that fixed, a [tool.ruff] configuration was added and the repository's 187 pre-existing lint violations were cleared to zero: 66 by ruff --fix (diff reviewed in full first), 35 by adding a TYPE_CHECKING-guarded import for a dynamically-loaded class annotation, 27 by prefixing genuinely unused variables with _ rather than deleting their (side-effecting) assignments, and the rest by small, behavior-preserving rewrites (splitting semicolon-joined statements, renaming an ambiguous l to kw, switching a type comparison to is).

Phase 1 — CI and packaging

The CI workflow gained a Python version matrix (3.10, 3.12) and a ruff check step, retiring an eleven-line comment that had deferred linting indefinitely. The nrel-pysam pin moved from a CI-only install flag into pyproject.toml's own dependency list (==7.1.0), so the package now declares its own PySAM version rather than relying on the CI script to enforce it.

Phase 2 — DealConfig becomes a validated contract

The repository already shipped a complete JSON Schema for its public deal-config input type, but nothing ever checked a dict against it — DealConfig.from_dict only pulled two required keys and let everything else through unchecked. A new reopt_pysam_vn.analysis.validation module implements a small structural validator (required fields, type checks, enum checks — the only three keywords the schema actually uses) with no new runtime dependency, matching the schema file's own documented promise. It is wired into from_dict as the default path, with an explicit opt-out (validate=False) that preserves the old bare-KeyError behavior for callers that want it.

Phase 2 — verification against the live webapp

The plan flagged a specific risk: the webapp's own /deals/new form builds a dict that the new validator could reject on a field the form and the schema disagree about. Rather than assume compatibility, the full webapp test suite was run after wiring the validator in — all 72 tests passed unchanged, including the test that already expects a validation error on a missing case field and the Samsung/TTC golden-parity test that exercises the complete web-API-to-library round trip.

07 / Findings & Recommendation

Findings & Recommendation

Both phases completed with zero regressions. The full portable test suite grew from 589 to 606 passing tests (the 17 added by Phase 2), with the same 18 deselected and 3 pre-existing xfailed tests unchanged throughout. ruff check went from 187 violations to zero and stays there; mypy stayed clean on the analysis and webapp public surfaces across both phases.

Tradeoff considered and rejected: using ruff's --unsafe-fixes flag would have auto-resolved the remaining violations faster, but several of them (unused-variable assignments with side-effecting right-hand sides) are exactly the class of fix that tool flags as unsafe for a reason. Manual, reviewed fixes were used instead.

Tradeoff considered and rejected: adding jsonschema as a dependency would have been the conventional way to validate against a JSON Schema file, but the schema's own description explicitly promises no runtime dependency is required, and only three of its keywords are actually used. A ~120-line hand-rolled validator keeps that promise instead of quietly breaking it.

Recommendation: proceed to Phase 3 next. It reconciles the Samsung/TTC parity gate — today both CI-excluded and xfailed while the README still describes it as enforced — and the plan requires reading its own diagnosis report before deciding whether to restore the gate or correct the documentation, so it is a bounded, well-specified next step.

09 / Risks / Open Questions

Risks / Open Questions

Open, unchanged by this work

  • The NREL Developer API key committed historically in two old commits has still not been confirmed rotated. This predates both phases in this report and is explicitly out of scope for this plan; it remains documented in README.md's security note.
  • Phases 3–6 of the plan are unexecuted. In particular, the Samsung/TTC parity gate's actual enforcement state (Phase 3) and the four-way currency-rate divergence (Phases 4–5) remain exactly as the original research brief described them.

Risks carried into future phases

  • No Python 3.10 interpreter was available to run the actual test suite locally during this work — only ruff's target-version syntax check was used as a proxy. The real CI run on the 3.10 matrix job is the first live confirmation that the full suite (not just syntax) passes there.
  • Phase 4's plan explicitly flags that the Julia VNData struct is positional, so a future field insertion done without running Julia's Layer 3 cross-validation could silently mis-assign fields with no error. This did not arise in Phases 1–2 but is a live risk for Phase 4 onward.
