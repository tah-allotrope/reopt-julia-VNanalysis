01 / Executive Summary

Executive Summary

What was done

A new reopt_pysam_vn.analysis package gives the repo one front door: a shared DealConfig input and result contract, run_onsite / run_offsite_dppa pipelines, and a python -m reopt_pysam_vn.analysis CLI. Five committed phases, each with its own report.

Why it matters

Before, analyzing a new Vietnam project meant cloning a 200–1,000-line case module. Now it means writing a config and calling a pipeline. The offsite economics were the same engine all along; Sprint 3 made it reusable and addressable.

The proof

The generalized run_offsite_dppa reproduces the bespoke Samsung-TTC combined-decision bit-for-bit. The onsite coverage matches the bespoke ninhsim summary exactly. The CLI ran the real Samsung pipeline end-to-end.

Honest edges

Case modules are deprecated as direct entry points (docs) but not yet reduced to thin wrappers — that inversion is staged to protect the proven parity and existing tests. Only Samsung is parity-gated so far.

02 / Background & Objective

Background & Objective

The 2026-06-12 gap analysis flagged GAP-01/06: the repo's key function — using REopt and PySAM to analyze onsite and offsite/DPPA Vietnam projects — existed only as bespoke per-deal modules (dppa_case_1/2/3, dppa_samsung_ttc, ninhsim_solar_storage_60pct), each with its own analyze script and tests. Adding a future project meant cloning one. Sprints 1–2 de-bloated and de-duplicated the repo; Sprint 3 is the one that touches tested logic.

The objective: a generalized, first-class onsite pipeline and offsite/DPPA pipeline, each driven by one config, with a CLI — and a parity gate proving the generalization didn't change any published numbers before any bespoke module was retired.

05 / Methodology

Methodology

Each pipeline reused the proven primitives rather than re-deriving them, and pinned its output to the bespoke logic with an exact equality test. The decisive method for the parity gate was to run an exploratory diff first — measure the real deviation (it was 0.0) before writing assertions — so the gate matched reality instead of a guessed tolerance. The offsite pipeline routes through an extensible registry to the proven Samsung builder, which the CLI exercised end-to-end; a from-scratch generic orchestrator (which needs a solve) was declined rather than faked.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — Generalization changed nothing numeric. The offsite pipeline reproduced the Samsung golden bit-for-bit and the onsite coverage matched ninhsim exactly. The gap analysis was right: these were one engine wearing five costumes.

Finding 2 — "Wrapping" hit a real direction problem. The new front door delegates to the case builder via a registry, so making that builder wrap the front door would be circular. The honest move was to ship the front door + deprecate via docs, and stage the code-inversion — rather than force a risky 1,000-line move that could break proven parity.

Recommendation. Adopt reopt_pysam_vn.analysis as the entry point for all new onsite/offsite work now. Schedule the follow-up cycle to invert the delegation (move orchestration into analysis/, reduce case modules to warning-wrappers, then remove) and to parity-gate the remaining four cases.

09 / Risks / Open Questions

Risks / Open Questions

Residual risks

  • Two front doors temporarily. Until the inversion lands, both the case modules and analysis are callable; docs steer to analysis, but discipline is required.
  • Single parity gate. Only Samsung is diff-pinned; a change to the shared engine could drift the other cases undetected by the new tests (their own tests still guard them).
  • Generic offsite path unbuilt. A brand-new deal with no registered orchestrator errors out by design until the solve-backed generic builder lands.

Open questions

  • Schedule the delegation inversion next cycle or batch with the wider parity gating?
  • Should the generic orchestrator drive a real REopt/PySAM solve, or accept injected results only?
  • When to delete the case modules entirely (post-wrapper cycle)?
