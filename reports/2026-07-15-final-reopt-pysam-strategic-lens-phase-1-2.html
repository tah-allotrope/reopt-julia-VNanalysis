01 / Executive Summary

Executive Summary

What was done

Two of the six phases in plans/2026-07-14-reopt-pysam-strategic-lens-plan.md were implemented, verified, and pushed to main as commits d8349e6 (Phase 1) and 7255ca9 (Phase 2). Phase 1 gave the internal web app — now the primary way non-technical colleagues run deals — an operator story: structured logging, a per-run provenance.json record, analyst-facing error messages instead of raw stack-trace text, and a manual run-pruning command. Phase 2 turned the toolkit's existing type hints into an enforced contract: a mypy gate on the analysis and webapp packages, a py.typed marker, and a new GitHub Actions CI workflow.

Why it matters now

The web app recently became the primary interface for Allotrope colleagues who are not software engineers. Before this work, a failed run showed them a raw Python exception message, nobody could tell which NREL API key or policy-data vintage produced a given result, and the type hints throughout analysis/webapp were decorative — nothing enforced them, so a refactor could silently violate a function's own contract. Phase 2's type check caught exactly that: a real, previously-invisible bug in the onsite scenario builder.

02 / Background & Objective

Background & Objective

reopt-pysam is a Vietnam DPPA (direct power purchase agreement) techno-economic toolkit: it models onsite behind-the-meter solar+storage economics via the NREL REopt API, and offsite/DPPA developer finance via PySAM, behind a shared DealConfig descriptor. A FastAPI web app shipped on top of it in July 2026 so deal analysts could run the whole workflow without a terminal.

A prior brainstorm and plan (dated 2026-07-11) had already diagnosed the toolkit's foundational debt — an unrotated leaked API key, no CI, five known-failing tests, and a single-tenant offsite path — but that plan remained unexecuted. Rather than duplicate it, a follow-on strategic-lens brainstorm (2026-07-14) looked past that debt-paydown work to four higher-altitude questions: is the web app operable day-to-day, are the type hints actually enforced, can the toolkit run offline, and is Julia still a load-bearing part of the stack or a stale artifact. This report covers the first two of those four themes, translated into the strategic-lens plan's Phase 1 (operational readiness) and Phase 2 (type gate).

Objective for this session: implement Phases 1 and 2 of that plan end-to-end — code, tests, and verification — commit each phase separately only once its tests are green, and push both to main.

04 / Assumptions & Constraints

Assumptions & Constraints

Constraints honored

  • Samsung/TTC settlement output is bit-exact gated by two test files; neither Phase 1 nor Phase 2 touches settlement math, and both parity tests were re-run and show the identical, unchanged pre-existing failure signature before and after this work.
  • The web app must never fork analytics logic into itself — Phase 1's provenance/error work only wraps existing analysis/service calls, it does not duplicate them.
  • PySAM only exists in the repo's own .venv (Python 3.12); all verification ran through that interpreter.

Judgment calls made in-session

  • The plan's literal error-taxonomy table would have genericized REopt solve-failure messages (e.g. "infeasible"); that was deliberately narrowed to keep those diagnostics visible, since a pinned existing test asserts on that exact text and hiding it would be a UX regression, not an improvement.
  • The CI workflow's ruff check step was intentionally deferred rather than added red — ruff has no project configuration yet and currently reports 181 pre-existing findings plus a hard crash parsing a malformed .gitignore glob, both squarely inside the separate 2026-07-11 plan's scope.
  • A minimal .github/workflows/ci.yml was created from scratch (per the plan's own binding-default instruction) since the separate foundation plan that would otherwise own CI setup has not yet run.
05 / Methodology

Methodology

Each phase followed the same loop: implement the code change, write or extend tests for it, run the relevant test suite, fix any failures, then run progressively wider verification before committing. "Never commit red" was treated literally — every failure encountered was individually triaged to determine whether it was caused by this session's changes or was a pre-existing condition, using git stash and a disposable git worktree at the pre-Phase-1 baseline commit (fd8ceaf) to reproduce failures in isolation before concluding they were unrelated.

That discipline surfaced two genuine surprises along the way (detailed in Section 07): a real, previously-latent bug that mypy caught in the onsite scenario builder, and a previously-undiscovered hang in an unrelated smoke test that both predates this session's work and was confirmed to reproduce identically on the original baseline commit.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 1 — Web-App Operational Readiness Done

Commit d8349e6. Delivered:

  • Structured logging — a shared configure_logging() replaces the app's mix of unconfigured loggers and 14 bare print() calls in library code (the 3 that actually fire during normal execution, inside the NREL solve poll loop, were converted; the rest were confirmed to be script-only or docstring examples and left alone).
  • Per-run provenance — every completed run now writes a provenance.json recording which solver ran (live NREL API, cache hit, or offline), a SHA-256 fingerprint of the API key used (never the key itself), cache hit/miss, wall-clock solve time, and the active Vietnam policy-data version for every file in data/vietnam/manifest.json.
  • Friendly errors — internal exceptions now map to a {code, message, hint} triple shown on the run page, instead of a raw Python exception string. Known, actionable failures (missing inputs, no registered orchestrator, no API key, a REopt solve rejection) keep their specific, useful message; only genuinely unexpected exceptions get a generic message pointing at the server log.
  • Run pruning — a new python -m reopt_pysam_vn.webapp.prune command lists (dry-run by default) or deletes terminal-state runs older than a given age; it never touches a run that is still queued, solving, or analyzing.

Phase 2 — Type Gate & Public-API Boundary Done

Commit 7255ca9. Delivered:

  • A [tool.mypy] configuration with disallow_untyped_defs scoped specifically to the analysis and webapp packages — the toolkit's supported public surface — leaving the internal integration/reopt/pysam engines lenient for now.
  • A py.typed marker so downstream consumers of the package get real type information.
  • A documented public-API boundary: analysis and webapp are supported; everything else may change shape without notice. Recorded in both the analysis package docstring and AGENTS.md.
  • A new .github/workflows/ci.yml running the mypy gate and the non-network pytest suite on every push and pull request.

16 real type errors were found and fixed at their root cause — no blanket # type: ignore suppressions were used. One of those fixes corrected an actual latent bug (see Section 07).

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — a real bug, found by adding types, not by looking for bugs. analysis/onsite.py was passing voltage_level=site.get("voltage_level") — which evaluates to None whenever a deal's site data has no voltage level set — directly into apply_vietnam_defaults(). That function has a real, documented default (medium_voltage_22kv_to_110kv) for exactly this situation, but passing an explicit None argument silently overrides the default instead of triggering it. Every onsite deal submitted without an explicit site voltage was quietly getting None where the toolkit's own documented convention says it should fall back to a sensible default. The fix (three lines: only pass the argument when a value is actually present) is committed in 7255ca9.

Finding 2 — a previously undiscovered, pre-existing test hang, unrelated to this work. While tracing why a full-suite run was taking far longer than the ~15s/~60s the project's own docs describe, a specific test — test_regime_matrix_no_solve_writes_complete_artifacts in tests/python/integration/test_regime_engine_smoke.py — was found to hang indefinitely (confirmed past 3 minutes with no completion). This was verified to be completely unrelated to Phases 1–2: it was reproduced identically in a disposable git worktree checked out at fd8ceaf, the commit immediately before any of this session's work. It is a genuine, previously-unknown issue in the regime-matrix scenario builder (called with solve=False, so it is not a live-network hang) that this session did not introduce and did not attempt to fix, since root-causing it is outside Phase 1/2's scope.

Finding 3 — the known red-test backlog is unchanged. All five test failures documented as pre-existing in activeContext.md (two Samsung/TTC parity assertions, one PVWatts capacity-factor benchmark, one ninhsim benchmark, and one strike-price-discovery test) were individually reproduced during this session's verification, with identical failure values both before and after Phases 1–2. Neither phase changed, fixed, or worsened any of them — they remain exactly where the separate, unexecuted 2026-07-11 plan left them for its own remediation pass.

09 / Risks / Open Questions

Risks / Open Questions

Open questions carried forward

  • Is anyone still solving locally in Julia? This gates whether Phase 5 (archive-in-place) can proceed as planned.
  • The test_regime_engine_smoke.py hang (Finding 2) has not been root-caused — it needs its own investigation, separate from this plan.
  • The new CI workflow has not yet been observed running on GitHub Actions itself (this session verified all steps locally); its first real run should be watched once pushed.

Risks and mitigations already applied

  • Risk: a type-safety fix could silently change Samsung/TTC's bit-exact output. Mitigation: the parity tests were re-run after every touch to dppa_samsung_ttc.py and onsite.py, and produced byte-identical (still pre-existing-failing) results before and after.
  • Risk: shipping a CI workflow that is red on day one. Mitigation: the ruff check step was deliberately omitted rather than added broken; only the verified-green mypy and pytest steps are included.
  • Risk: mistaking a pre-existing failure for a regression (or vice versa). Mitigation: every failure encountered was checked against a disposable git worktree at the pre-session baseline commit before being classified.
